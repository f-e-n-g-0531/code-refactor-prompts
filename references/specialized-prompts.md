# 专项变体提示词

每个变体只写「与主模板不同」的部分；骨架、硬约束、验收标准、输出格式沿用 SKILL.md 主模板。

## 1. 性能优化（先分析，后最小改动）

```text
你现在是性能优化专家。保持行为等价，先分析、后做最小改动。

当前问题：{例如：首页加载 5 秒}
目标：{例如：< 2 秒}
技术栈：{语言 + 框架 + 构建工具}

请按步骤：
1. 列出至少 5 个可能瓶颈，按影响程度降序（表格形式）；
2. 只实现收益明确的 Top 3，逐项说明预期收益与代价，不做微优化；
3. 对比优化前后的时间/空间复杂度与内存占用；
4. 若没有真实优化空间，明确说明，不要为了改而改。

输出：瓶颈分析 → 优化方案(含代码) → 预期效果(数据对比)。
```

## 2. 代码坏味道（识别优先，逐个给重构手法）

```text
你是代码评审专家。识别以下代码的 code smell（长方法、大类、长参数列表、重复代码、依恋情结、数据泥团、散弹式修改、Primitive Obsession 等），
并逐一给出可落地的重构方案（Extract Method / Introduce Parameter Object / Replace Conditional with Polymorphism / Replace Magic Number with Symbolic Constant 等）。

按「问题 → 位置 → 严重度 → 建议重构手法 → Before/After → 风险」输出，先列完整清单再给改动。
```

## 3. 大文件 / 长函数拆分

```text
这段代码约 {行数} 行，`{函数/类名}` 过长、职责混杂。请在不改变行为的前提下拆分重构：
1. 按单一职责拆分函数/类，每个单元职责单一；
2. 给出拆分后的模块划分与职责边界；
3. 说明拆分后单元测试如何组织；
4. 输出拆分方案 + 各单元代码 + 集成方式。
```

## 4. 安全加固

```text
你是安全专家。在不改变正常输入行为的前提下加固以下代码：
1. 检查注入（SQL/命令/模板）、XSS、越权、敏感信息泄漏、不安全反序列化、弱校验；
2. 按 OWASP 检查，列出「问题 → 严重度 → 修复」；
3. 修复需保持原有功能，并说明是否影响外部行为。
```

## 5. 现代化升级（追平语言新特性）

```text
你熟悉 {语言} 的现代特性。在行为等价的前提下，把以下代码升级到 {目标版本} 的惯用写法：
1. 用现代语法/API 替换过时写法，逐项说明等价性；
2. 不引入破坏性不兼容变更；
3. 标注每个新特性的引入版本。
```

## 6. 分语言定制要点

把「测试命令 + 惯用重构手法 + 红线」替换进主模板对应占位符。速查如下，完整版见 `references/language-specific.md`。

| 语言 | 测试/检查 | 惯用重构目标（节选） | 红线 |
|------|-----------|----------------------|------|
| Java | mvn test / gradle test | Stream+Collectors、Optional 去 null、record、sealed+switch、try-with-resources | 签名不变；Optional 不放 null |
| Python | pytest；ruff / mypy | 推导式、with、类型注解、dataclass、match/case、pathlib | 可变默认参数；闭包晚绑定 |
| JS/TS | npm test；tsc --noEmit | const/let、解构、async/await、类型收窄、?. 与 ?? | 别滥 !/any；改 async 保错误语义 |
| React | npm test | Class→Hooks、自定义 Hook、按职责拆分 <100 行 | 依赖数组完整；Hook 顺序稳定 |
| Go | go test；go vet；golangci-lint | 小接口、显式错误、context、组合 | 忽略 error / 滥用 panic；签名不变 |
| Rust | cargo test；clippy；fmt | enum 令非法态不可表示、Result+?、借用优先、组合子 | 去 unwrap；不随意 unsafe |
| C#/.NET | dotnet test；dotnet format | 启用 NRT、record、LINQ、switch 表达式、CancellationToken | 绝不 .Result/.Wait() |
| SQL | 执行计划对比 | 消 N+1、参数化、CTE、明确索引 | 结果集等价；NULL 语义不变 |
| C++ | CTest/GoogleTest；clang-tidy | RAII、智能指针、算法库、move 有度 | 不引入 UB/悬垂；生命周期语义不变 |

## 7. 行为基线测试（characterisation test）

```text
你是测试专家。在重构下面的 {函数/模块} 之前，先生成「行为基线测试」：
1. 捕捉当前实际行为，哪怕它看起来像 bug（只记录、不评判）；
2. 覆盖 happy path 与关键边界情况；
3. 用测试名表达「当前实际行为」，而非「期望行为」；
4. 框架：{Jest / pytest / JUnit}，必要时 mock 外部依赖。

这套测试是重构的安全网：重构后它必须全部通过，否则说明行为被意外改变。
```

## 8. 守卫（Guard Clauses）

在任意提示词末尾追加守卫分支，让模型在无输入/无需求时明确拒绝而非硬凑：

```text
若无代码提供：输出 NO_CODE_PROVIDED，并索要代码。
若代码无明显问题：输出 NO_REFACTORING_NEEDED，说明理由，不要为了改动而改动。
```

## 9. 可测试性改造（先使人能测，再使人会测）

```text
你是可测试性专家。分析以下代码的可测试性障碍，给出不改变行为的改造方案：
1. 硬编码依赖：直接 new 实例化、静态调用外部服务、全局状态/单例、硬编码路径/配置；
2. 紧耦合：依赖具体实现、领域逻辑里直连 DB/框架、隐藏依赖、服务定位器；
3. 状态问题：可变全局、静态可变字段、顺序依赖（temporal coupling）；
4. 可见性：逻辑复杂的私有方法难以直接测试。

改造手法：构造器/Setter 注入、抽取接口、工厂/策略模式、参数对象、纯函数化、不可变对象、提取 seam。
验收：改造后原有行为不变，并用 {测试框架} 为关键路径补单元测试；逐项说明「改动如何提升可测性」。
```

## 10. 模块化 / 解耦

```text
你是模块化与解耦专家。分析以下代码的耦合与内聚问题，并从最差到最好排序：
- 耦合：内容耦合 > 公共耦合 > 控制耦合 > 标记耦合 > 数据耦合（最好）；
- 内聚：偶然内聚 < 逻辑内聚 < 时间内聚 < 过程内聚 < 通信内聚 < 顺序内聚 < 功能内聚（最好）。

改造手法：依赖倒置/依赖注入、接口隔离（小而聚焦）、门面/中介者、事件驱动解耦；消除循环依赖与「改一处动全身」的散弹式结构。
输出：耦合/内聚问题清单（含位置）→ 目标模块边界 → 逐项改造，并说明如何减少波及面。
```

## 11. SOLID 原则

```text
你是架构专家。逐一核对以下代码的 SOLID 违规并给出落到具体重构手法的改造：
- SRP 单一职责：一个类只应有一个变更原因；检测 god class（>500 行）、同时混业务+持久化+UI 的类；
- OCP 开闭：对扩展开放、对修改关闭；检测基于类型判断的 switch/if-else 链、写死依赖；
- LSP 里氏替换：子类不得加强前置条件/削弱后置条件/抛基类不抛的异常；
- ISP 接口隔离：小而聚焦的接口，避免「胖接口」；
- DIP 依赖倒置：依赖抽象而非具体实现。

对应手法：Extract Class / Move Method / 策略模式 / 模板方法 / 注入 / 接口拆分。
输出：违规项 → 位置 → 违反哪条 → 建议手法 → Before/After。
```

## 12. 设计模式应用

```text
你是设计模式专家。阅读以下代码，只在确有收益时引入 GoF 设计模式，避免「为了用模式而过度设计」：
- 创建型：Factory / Abstract Factory / Builder（构造 >5 参数）/ Singleton（慎用）；
- 结构型：Adapter（接老代码/第三方）、Facade（简化子系统）、Decorator、Composite（树结构）、Proxy（懒加载/访问控制）；
- 行为型：Strategy（替换 if-else 类型分支）、Template Method、Observer、Chain of Responsibility。

对每个建议给出：当前症状 → 候选模式 → 为什么合适 → 改造后结构；若无需模式，明确说「现有设计足够，不必引入模式」。
```

## 13. 技术债 / 遗留系统

```text
你是技术债治理专家。对以下代码做债务盘点并给出可落地还债路线图：
1. 代码债：坏味道、圈复杂度 >10、深层嵌套 >4、魔法数字、死代码、命名；
2. 设计债：边界被打破、紧耦合、低内聚、SOLID 违规、单体化；
3. 测试债：覆盖率 <80%、缺关键路径测试、flaky/慢测试、无断言；
4. 文档债：缺 README/API 文档、文档与实现脱节。

先锁行为基线（见第 7 节），再增量还债；优先级从「价值优先 / 风险优先」二选一。
输出：债务清单（按严重度）→ 每项影响与还债成本 → 分阶段路线图 → 每阶段验证方式。
```
