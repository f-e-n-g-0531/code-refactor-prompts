# 端到端重构工作流

本文件补充「提示词之外」的操作流程：什么时候先评审、什么时候先补测试、大范围重构怎么分批、AI 输出应用后如何迭代修复。核心模板仍以 SKILL.md 为准；每条工作流给出可直接复制的提示词片段。

## 工作流 1：先评审，再重构（Review → Plan → Refactor）

适用：已有重构任务，但不确定改动范围与优先级。

1. **评审**：让模型只读不改，产出带行号的分级问题清单。

```text
请只做代码评审，不要改代码。逐条列出问题：严重度(高/中/低) → 位置(文件:行号) → 问题 → 建议手法。
输出按严重度排序的问题清单，不要给完整代码。
```

2. **计划**：把高/中问题转成分批计划，每批一个可独立验收的小目标。
3. **重构**：按批套用 SKILL.md 主模板，每批单独给【验收标准】。
4. **验证**：每批通过后再进入下一批；任何一批失败先回滚该批。

## 工作流 2：遗留 / 无测试代码（先锁行为基线）

适用：历史代码没有测试、行为不完全清楚——这是最危险的重构场景。

1. **生成行为基线测试**：

```text
为下面的代码生成「行为基线测试」：目标是捕捉它当前的真实行为（即使看起来像 bug 也要如实断言），不要修正行为、不要改被测代码。
- 覆盖：正常路径、边界值、异常路径、当前实现中的特殊分支；
- 断言要具体（给定输入 → 期望输出 / 期望异常）；
- 测试必须在当前代码上直接通过。
{粘贴代码}
```

2. **确认基线**：本地跑通这批测试并提交，再开始重构。
3. **重构**：主模板 + 硬约束「行为基线测试必须原样通过」。
4. **差异复核**：若基线测试需要修改才能通过，说明发生了行为变化，必须逐条解释。

## 工作流 3：多文件 / 大范围重构（盘点 → 分批 → 验收）

适用：跨模块、跨文件的系统性重构（去循环依赖、统一错误处理、替换基础设施）。

1. **盘点**：先让模型列出影响面清单（调用方、测试、配置、文档），不要直接改。
2. **定序**：按依赖方向分批——先改叶子，再改调用方；每批保持编译/测试绿。
3. **分批提示**：每批只给该批文件与目标，明确「本批不越界改其他文件」。
4. **每批验收**：全量测试 + 静态检查；每批一个提交，便于回滚。
5. **收尾**：删除过渡期兼容代码（如有），再跑一次全量验证。

## 工作流 4：应用 AI 输出后的迭代修复

适用：模型给出的重构代码不能一次通过测试。

1. **应用**：按 diff 逐块应用，应用前确保已提交或已备份。
2. **跑测试**：收集完整失败输出（不要只贴第一行）。
3. **回喂**：只给失败用例 + 相关代码片段 + 已做改动摘要，不要重贴全部代码。

```text
下面是重构后的代码与测试失败输出。请只修复导致失败的最小改动，不要顺带改其他逻辑。
【失败输出】...
【相关代码】...
【约束】保持已通过的用例继续通过。
```

4. **收敛**：连续两轮仍失败 → 回滚该批，缩小重构步长（先拆更小的目标）。
5. **记录**：把失败原因写进提交说明，避免同类问题再次出现。

## 流程层面的反模式

- 没有基线测试就先大改 → 行为回归无法发现。
- 一次让模型改几十个文件 → 评审成本高于收益，失败点无法定位。
- 让模型「跑测试」却不给测试命令 → 模型只能编造结果。
- 失败后重贴全部代码重来 → 丢掉已通过的进展，且容易引入新问题。
